# Simple freelancer flow

The employer work map opens with Freelancer → Agreement → Task → Submitted work.
A payment card sits below the work. Revision requests appear only when they exist;
each shows its own proposed or approved fee. The latest submission is shown by
default, with an earlier submission retained when visible feedback refers to it.
Older history, uploaded files, AI assistance and organization tools remain available
through **Details & tools** and the existing project panels.

Cards and people remain draggable. Connections use measured node bounds and four
possible sides, with straight aligned paths, curved diagonal paths and hysteresis
near equal routing choices. Pan, zoom, fullscreen, saved coordinates and existing
relationships are preserved. Overlapping/contained nodes can obscure part of a
line; separating them restores a clear route. This is endpoint routing, not an
obstacle-avoidance router for every unrelated object on a large board.

## Dedicated example

Select **CrewCanvas · Simple Freelancer Demo** using the existing Team Client
login. It contains one **Video Editor**, one **30-Second Promotional Video**
project, a proposed **$50** agreement, and one task:
**Edit and submit the promotional video**. The proposed deadline is November 8,
2026, with one included revision round. The brief is explicitly a non-binding
synthetic exercise. No submission, revision, invoice or payment is seeded.

The existing Freelancer 1 test login acts as Video Editor only in this workspace.
Its identity and memberships in other workspaces are unchanged. The other two
freelancers have not been added: the employer can invite them manually later.
Credentials and provisioning state remain in ignored local files, never GitHub.

## Manual check

1. Client: click the freelancer for project, task status, deadline, fee and latest
   work; click the agreement to review the terms.
2. Video Editor: select this workspace and review/accept the proposed agreement.
   Submit one uploaded deliverable or a supported Drive link.
3. Client: use **Approve Work** or **Request Revision**. Requesting a revision
   creates feedback only and never creates a fee or invoice.
4. Video Editor: accept feedback as included, ask for clarification, or propose a
   revision fee. A pending $10 fee leaves an accepted $50 total at $50.
5. Client: approve or decline the fee. Approval updates the accepted agreement to
   $60 exactly once; decline keeps it at $50. Approval is not payment.
6. Inspect the revision card and payment breakdown. Paid appears only from
   server-verified PayPal Sandbox settlement; sample history cannot earn a verified
   paid badge. New demo seller setup is separate from the previously verified test
   merchant. No automatic seller reassignment or new payment is performed.
7. Drag cards, zoom, pan, enter fullscreen, refresh and confirm persistence.
8. Add two freelancers manually using their own existing test-account emails and
   create projects when desired. No tasks or project structures are generated by
   inviting a person.

## Deployment and rollback

The API catalog adds authorized `submission:<projectId>` placeholder IDs and
validates their workspace relationships. No schema, RLS, payment-provider or Auth
settings change. Existing API authentication is preserved. Keep this additive
catalog support when reverting the frontend, because saved layouts may contain
placeholder coordinates. Frontend rollback otherwise uses the preceding Vercel
deployment; the detailed view is also available without a deployment.
